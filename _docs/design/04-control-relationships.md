# Design Step 4 — Control Relationships

_Status: Draft · 2026-09-29_
_Input: design steps 1–3 (`_docs/design/`), `_docs/prd.md`._
_Process: `_docs/agentic-systems-and-workflows.md`, Design process, Step 4. No framework is assumed._

Steps 1–3 describe what the system does. This step describes how it stays
trustworthy while doing it: memory, validation, termination, and human
involvement, per stage, plus the work that belongs to the outer control loop.

## 1. Per-stage control table

### Memory (relationship 3)

| | S1 Propose | S2 Oppose | S3 Decide |
|---|---|---|---|
| **Reads** | `motion`, `side=for` | `motion`, `side=against` | `motion`, `argument_for`, `argument_against` |
| **Writes forward** | `argument_for` | `argument_against` | `verdict` |
| **Persisted beyond the run** | `propose.md` | `oppose.md` | `decide.md` |

**Scoping rule.** Each call's inputs are built by the control loop from a
per-stage allowlist. A stage cannot read a key that is not on its list.

| Memory key | Readable by |
|---|---|
| `motion`, `run_id` | S1, S2, S3 (`run_id` is used by the loop only) |
| `argument_for` | S3 only |
| `argument_against` | S3 only |
| `verdict` | Nothing in the run. It is the final result. |

This is what enforces fairness (NFR-1): S2 is never handed `argument_for`,
even though S1 may finish first. There is no cross-run memory in v1. The
output files are the only thing that outlives a run.

### Validation (relationship 4)

Checks run on each stage's output before anything trusts it. Checks are
deterministic in v1.

| Stage | Shape checks | Content checks | On reject |
|---|---|---|---|
| S1, S2 | Non-empty text. Word count within 150–350 (the target is 200–300, with slack). | None automated (see the decision below). | Retry with the failure reason added to the call. |
| S3 | `winner` is exactly `for` or `against`. `reasoning` is non-empty and at least 50 words. | None automated (see the decision below). | Retry with the failure reason added to the call. |

**Recorded decision: no automated content checks in v1.** Two properties
cannot be checked deterministically: that a debater actually stayed on its
assigned side, and that the verdict's reasoning refers to the real points in
both arguments. A model-based check would need a third reasoning-core
configuration, which step 2 does not define. In v1 these are covered by manual
review on a sample (PRD success metrics) and the risk is accepted. Revisit if
side drift or vague verdicts show up in the sample. If added, it would be a new
configuration in step 2, not a patch here.

### Termination (relationship 5)

| | S1, S2 | S3 |
|---|---|---|
| **Success** | Output passes validation. | Output passes validation. |
| **Failure** | Not applicable (see run-level rule). | Same. |
| **Exhausted** | 3 attempts (first call plus 2 retries) all rejected, or the per-call timeout is hit on each attempt. | Same. |
| **Limits** | 3 attempts. 60 s timeout per call. A per-call output token cap sized for the length target. | Same. |

Each stage has no tools, so its inner loop is one call per attempt.

### Human interface (relationship 6)

| | S1, S2, S3 |
|---|---|
| **Approval needed** | No. |
| **Can ask a question** | No. The motion is the only input. |
| **Surfaced on exhaustion** | The run ends with an error naming the stage and the last rejection reason. |
| **If nobody answers** | Nothing waits, so there is no state to time out. |

## 2. Outer-loop concerns

These belong to the orchestrator that invokes stages, not to any stage.

### 2.1 Initial input entry

- **Who writes it:** the outer control loop, once, before S1 and S2 start.
  The first stage's memory row assumes memory already holds something to read.
- **What it writes:** `motion` and a generated `run_id`.
- **Checks before writing:** the motion is non-empty after trimming (FR-1.3).
  If not, the run is rejected with no model call and no folder is created.
- **`run_id`:** generated by the outer loop, safe as a folder name (timestamp
  plus a short slug of the motion). This answers the step 3 carry-forward.

### 2.2 Between-stage human steps

None. S1 and S2 run without a pause, and S3 runs as soon as both are valid.

### 2.3 Fork and join

- The outer loop starts S1 and S2 together and starts S3 when both are done
  (step 1). S3 never starts on a partial result (FR-5.1).
- **If one branch is exhausted:** the outer loop stops and does not run S3
  (FR-5.2). The run ends with a report of which stage failed and which
  artifacts exist. _Amended after design step 5, tests 4 and 4b:_ CrewAI ran
  S1 then S2 without overlap and aborts on the first exhausted stage, so a
  failed S1 leaves no other artifact, and a failed S2 keeps S1's. Each
  artifact is written as soon as its stage passes, so nothing finished is lost.

### 2.4 Writing artifacts

- The control loop renders each artifact as Markdown, then calls
  `write_artifact` (step 3). The rendering adds a heading with the motion
  and side (S1, S2) or a `Winner:` line (S3), so each file is readable alone.
  The validated stage output is the body. This answers the step 3 carry-forward.
- **Verdict format (PRD Q3, resolved):** a `Winner: For|Against` line, then the
  reasoning as free text.
- **When it runs:** right after each stage passes validation, so a later
  failure does not lose earlier results.
- **`WriteFailed`:** retried up to 3 times with a short backoff, without
  re-calling the reasoning core. If it still fails, the run ends as failed.
  Invalid-argument errors are bugs and end the run as failed at once.

### 2.5a Run report (PRD FR-7, added 2026-09-30)

Documented after it was first implemented. The design below is what the code
does, and it was checked against a real run.

- **Who owns it:** the outer loop. It is not a stage and needs no model call.
- **What is measured:** per stage, attempts and tokens (prompt, completion,
  total). Tokens come from the reasoning core's own usage counters.
- **Attribution rule:** the counters are cumulative and not split by stage.
  The outer loop snapshots the running total at every validation check, and
  what accrued since the previous check belongs to the stage being checked.
  This is correct only because stages run one after another (design step 1,
  as amended by step 5, test 4b). If stages ever ran at the same time,
  this rule would misattribute usage and would need to change.
- **Attempt:** one validation check, so a rejected and retried reply counts as
  another attempt. An error before validation (a timeout) is not an attempt.
  Tokens left over from such a call are added to the stage that was running
  when the run stopped.
- **Shared model instance:** two configurations may share one instance, so
  usage is summed over distinct instances, not per configuration.
- **When it is reported:** always, at the end of the run, including
  exhausted and failed runs, so an exhausted stage shows what its attempts
  cost. Success goes to standard output and other outcomes to standard error.
- **Known gap:** on a wall-clock timeout, the call still in flight is not
  counted, because the run was reported without waiting for it.
- **Not in v1:** cost in currency (PRD FR-7.7), and usage stored across runs.

### 2.5 After the last stage: human review

No review step in v1. The run ends when S3 passes validation and its artifact
is written. The outer loop reports the verdict location and stops. Because
nothing is reviewed or corrected, the four review questions (what the human
can do, how a correction re-enters, how a corrected artifact is protected,
whether edits are validated) have no answer to record yet.

The dependency map is already known if review is added later:

| Artifact corrected | Stale stages | Re-run starts at |
|---|---|---|
| `argument_for` (S1) | S3 | S3 |
| `argument_against` (S2) | S3 | S3 |
| `verdict` (S3) | None | Nothing to re-run |

S1 and S2 never make each other stale, because neither reads the other. Any
future review step would also need a `human-corrected` marker on artifacts and
the same validation on edits as on generated output.

## 3. Run-level termination

| Outcome | Condition |
|---|---|
| **Success** | S1, S2 and S3 all passed validation and all three artifacts are written. |
| **Exhausted** | A stage used all 3 attempts, or the run exceeded its limits. |
| **Failed** | An artifact write failed after retries, or an invalid-argument error occurred. |

**Run limits.** At most 9 model calls (3 stages times 3 attempts). Wall-clock
limit of 5 minutes for the whole run. Hitting either limit is *exhausted*.
Every outcome other than success reports the failing stage and reason, and
leaves the artifacts already written in place.

## 7. Update (feature 002): the order check

With `--check-order` (PRD FR-9), S4 Decide (swapped) runs after S3 (design 01,
section 7). Without the flag nothing below applies.

**S4's control table**

| | S4 Decide (swapped) |
|---|---|
| **Memory** | Reads `motion`, `argument_for`, `argument_against`, in that reversed order. **Never** the verdict. Writes `swapped_verdict`, persisted as `decide_swapped.md`. |
| **Validation** | The same verdict guardrail as S3. |
| **Termination** | 3 attempts, 60 s per call. Exhausted means "check not completed", **not** a failed run. |
| **Human interface** | None. |

**Different failure rule.** S1 to S3 keep their rule: an exhausted stage ends the
run. S4 does not. If `decide` has completed and been saved, and only
`decide_swapped` is missing, the run **succeeds** with the check reported as
not completed. This holds for a swapped verdict rejected 3 times, the time limit
reached during S4, an error from the call, and a failed write of
`decide_swapped.md`. A failed write of the official `decide.md` still fails the
run. The rule is one shared function, asked on every path that ends a run.

**Outer-loop step: compare the verdicts.** The winner is a side, not a position.
Same winner in both orders is **stable**. A different winner is **sensitive**:
official `for` then swapped `against` means the judge favored the argument it
read first; official `against` then `for` means it favored the one it read last.
The official verdict is never changed. A change of winner is the reading order or
ordinary variation between judge calls, and one swap cannot separate the two.

**Limits.** The model-call cap is 12 with the check (4 stages, 3 attempts each),
9 without. The 5-minute wall clock is unchanged. S4's attempts and tokens are
recorded under `decide_swapped`, so the run report (section 2.5a) and the batch
budget include them.
